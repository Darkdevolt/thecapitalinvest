**Périmètre :** code du dépôt (`public/`, `api/`, `lib/`, `.github/workflows/`) + base Supabase

## 0. Ce que ça change par rapport aux audits précédents

Les trois audits précédents laissaient deux questions de sécurité ouvertes en priorité
haute, « non vérifiables depuis le dépôt seul ». Elles le sont maintenant :

| Question ouverte depuis le 21 août | Réponse vérifiée le 12 septembre |
|---|---|
| Les RPC de paiement comparent-elles `p_user_id` à `auth.uid()` et recalculent-elles le montant côté serveur ? | **Oui, sur les deux points.** `create_payment_order` et `submit_payment_proof` lèvent une exception si `auth.uid() <> p_user_id`. Le montant facturé vient de `billing_plans`, jamais du client — `p_claimed_amount` n'est qu'une preuve déclarative que l'admin vérifie manuellement, il n'écrase jamais `amount`. |
| Les policies RLS protègent-elles les tables de marché en écriture ? | **Oui.** `cours`, `historique`, `indices`, `entreprises`, `financials`, `dividendes_calendrier`, `boc` : lecture publique (`anon`+`authenticated`), écriture conditionnée à `is_admin()` ou `private.tc_is_admin()` sur les quatre opérations (INSERT/UPDATE/DELETE). `transactions`, `watchlist`, `alertes_cours` : bien scopées au propriétaire (`auth.uid() = user_id`) ou admin. |

Ce sont de bonnes nouvelles. En contrepartie, cette passe a trouvé une régression de
sécurité réelle et deux bugs silencieux actifs, détaillés ci-dessous.

## 1. Régression — les en-têtes de sécurité ont disparu de `vercel.json`

L'audit du 21 août (§2.6) avait ajouté `X-Content-Type-Options`, `X-Frame-Options`,
`Strict-Transport-Security`, `Referrer-Policy` et `Permissions-Policy`. Le `vercel.json`
actuel ne contient **plus aucun de ces en-têtes** — seuls des réglages de cache et deux
rewrites subsistent. Il a visiblement été réécrit depuis (12 commits successifs de
`fix(vercel)`/`fix:` touchant routage et cache), et la version qui a gagné n'a jamais
repris le bloc sécurité.

Le fichier `vercel.json.new`, resté à la racine, contient l'ancien bloc — c'est un
brouillon obsolète (comparé ligne à ligne : il n'a ni le `buildCommand`, ni les règles
de cache actuelles), pas la source de vérité. Il faut réintégrer les en-têtes dans le
`vercel.json` réellement déployé, pas restaurer ce fichier.

De la même manière, il n'y a **plus de bloc `crons`** dans `vercel.json`. Si le
traitement automatique de `/api/process-brvm` à 16h05 en semaine (corrigé le 21 août,
§1.2) dépendait de cette déclaration, il est probablement inactif depuis. À vérifier :
si le déclenchement se fait maintenant autrement (dashboard Vercel, service externe),
ignorer ce point ; sinon, le cron est à rajouter.

**Action :** ajouter le bloc `headers` retiré + reconfirmer comment `/api/process-brvm`
est déclenché aujourd'hui.

## 2. Bug actif — l'onglet « Paramètres » de l'admin est silencieusement vide

`public/admin/js/modules/parametres.js` lit la table `admin_settings` **directement en
PostgREST**, avec la session de l'administrateur (`TC.getAll('admin_settings', ...)`).

Cette table a RLS activé **sans aucune policy** (confirmé en base). Par défaut, RLS sans
policy refuse tout accès — y compris à un administrateur authentifié. La table contient
pourtant une ligne réelle (le réglage `brvm_processing` que `api/process-brvm.js` lit et
écrit côté serveur, en `service_role`, qui lui n'est pas soumis à RLS).

Résultat : l'onglet Paramètres affichera toujours « La table admin_settings est vide »,
quoi que contienne réellement la table — exactement le symptôme silencieux que les
audits précédents mettaient en garde (§6.2 d'`AUDIT.md`).

Trois autres tables sont dans le même état (RLS activé, zéro policy), mais dormantes :
`brvm_scrape_runs` (son seul lecteur, `api/health.js`, passe par `service_role` — pas
d'impact), `per_history` et `the_capital_signup_otps` (aucun code applicatif ne les lit
encore).

**Action :** ajouter une policy `SELECT` sur `admin_settings` pour `authenticated` +
`is_admin()` (et `INSERT`/`UPDATE` si l'admin doit pouvoir modifier les réglages depuis
cet onglet). Verrouiller `per_history` et `the_capital_signup_otps` avec une policy
explicite avant de les brancher à un écran, plutôt que de les laisser dans cet état
ambigu.

## 3. Bug actif — un workflow GitHub Actions échoue à 100 % depuis sa création

`.github/workflows/oneoff-brvm-session-fix.yml` est déclenché `on: push: branches:
[main]` — **à chaque commit sur `main`**, sans exception. C'est un script de migration
« one-off » (il réécrit `brvm-market-hours.js`, retire la vue Formation, puis fait
`git commit && git push` lui-même) qui n'a jamais été retiré après son premier passage.

Vérifié via l'API GitHub : les 5 derniers runs (jusqu'à aujourd'hui, 12 septembre)
sont **tous en échec**. Cause probable : le script se termine par
`Path('public/app/js/views/formation.js').unlink()` sans garde — le fichier a déjà été
supprimé au premier run réussi, donc chaque run suivant plante sur un
`FileNotFoundError` avant d'arriver au `git push`. Ce n'est pas visible dans
l'application (le job échoue après action, ou avant — dans les deux cas rien n'est
poussé d'invalide), mais chaque commit sur `main` produit un ✗ rouge dans l'onglet
Actions du dépôt.

**Action :** supprimer ce workflow (son travail est fait, `formation.js` n'existe plus
et `brvm-market-hours.js` est en place) ou le passer en `workflow_dispatch` seul comme
`admin-cours-ui-patch.yml`.

## 4. Fonctionnalité fantôme — un module admin complet est invisible

`public/admin/js/modules/seances-excel.js` s'auto-enregistre (`TC.register({id:
'seances-excel', label: 'Séances & import Excel', ...})`) mais n'est chargé **par
aucune balise `<script>` dans `admin.html`** ni par la liste `EXTENSIONS` du chargement
différé (`admin/js/core/diagnostics.js`, qui ne charge que `abonnements`, `institute`,
`parametres`). Le module existe, fonctionne probablement, mais aucun administrateur ne
peut jamais l'ouvrir — le même défaut que le CHANGELOG (1.2.0) documentait déjà pour
quatre autres modules en août.

**Action :** décider s'il doit être branché (ajouter le `<script>` + l'entrée de menu)
ou archivé s'il est supplanté par un autre écran.

## 6. Vérifié sain — aucune action requise

- **Scan syntaxique** de tout `public/app/js/**` et `public/admin/js/**` : aucune
  erreur de parsing trouvée (les 7 fichiers cassés de l'audit du 21 août restent
  corrigés, rien de nouveau depuis).
- **Toutes les références de scripts/styles** (statiques et chargeurs dynamiques)
  résolvent vers un fichier réel, à l'exception du cas `seances-globales.js` ci-dessus.
- **Routage** (`router.js`) : les 23 routes ont toutes un conteneur `#view-<route>`
  dans `app.html` — le problème majeur de l'audit du 9 septembre (8 écrans sans
  conteneur) est résolu. Trois entrées du `renderMap` (`analyse-detail`,
  `financials-detail`, `analyse-technique`) pointent vers des fonctions qui n'existent
  pas sous ce nom exact, mais chaque vue est en réalité peuplée par un canal parallèle
  (`openAnalyseDetail()`, `openFinDetail()`, `atInit()`) — cosmétique : la vue
  s'affiche correctement, seule une boucle de relance de ~6 s tourne à vide en
  arrière-plan à chaque navigation vers ces trois écrans.
- **`api/*.js`** : les 12 routes utilisent uniformément la signature Node
  `(req, res)` — plus de trace du bug runtime Edge de l'audit du 21 août.
- **Nouvelles routes `obligations` et `documents`** (introduites depuis le 9
  septembre) : correctement câblées — conteneur, entrée de barre de navigation,
  fonction de rendu, toutes présentes.
- **Lien « Mot de passe oublié ? »** (`login.html`, flagué non branché le 9
  septembre) : implémenté, appelle bien `/auth/v1/recover` de Supabase.
