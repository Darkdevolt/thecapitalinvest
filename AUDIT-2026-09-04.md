## 2. Corrections vérifiées depuis l'audit historique

### 2.1 Router

Le routeur utilise désormais un sélecteur `data-route` commun pour déterminer les éléments de navigation actifs.

Le breadcrumb ne génère plus de `onclick="nav(...)"` pour sa navigation : il génère un attribut `data-breadcrumb-route` et un écouteur délégué prend en charge la navigation.

La gestion du hash, du `popstate`, des dropdowns, de la vue active et du breadcrumb reste centralisée dans `public/app/js/router.js`.

### 2.2 Shell et navigation

`public/app/js/shell-overhaul.js` centralise désormais les interactions résiduelles de compatibilité pour les anciens composants générés dynamiquement.

Le mécanisme accepte uniquement un ensemble explicite d'actions connues :

- navigation `nav()` ;
- détail financier `openFinDetail()` ;
- fiche titre `openFiche()` ;
- tri `sortTable()` ;
- activation/suppression d'alerte.

Il ne réexécute pas arbitrairement le contenu d'un ancien attribut `onclick`.

Les contrôles injectés ultérieurement par les vues sont également normalisés par `MutationObserver`.

### 2.3 Bootstrap

`public/app/js/init.js` utilise désormais `TC_ENV.getSession()` en priorité, avec repli de compatibilité vers `tc_session` dans `localStorage`.

Les modules secondaires sont chargés séquentiellement dans l'ordre déclaré au lieu d'être lancés simultanément en `async`.

Objectif atteint : supprimer la dépendance à la latence réseau pour l'ordre d'exécution des modules secondaires.

### 2.4 Build guard

Le garde-fou `scripts/check-assets.mjs` est exécuté par `npm run build`.

Le dernier build de production a confirmé :

> 23 pages, 147 scripts et garde-fous applicatifs vérifiés, aucune référence cassée, erreur de syntaxe ou invariant critique violé.

Cela invalide l'ancien état « scripts manquants non détectés » pour le périmètre couvert par ce contrôle.

## 4. Résidus techniques volontairement non supprimés

### 4.1 `window.tcSession` / `window.tcAccessToken`

Ils existent encore dans `app.html` et `init.js`.

**Décision actuelle : ne pas les supprimer.**

Ils constituent un pont de compatibilité pour les modules historiques. La migration vers une source de session unique doit être faite après cartographie exhaustive de leurs consommateurs.

La priorité est donc :

`TC_ENV.getSession()` / `TC_ENV.getToken()` → nouveaux modules  
`window.tcSession` / `window.tcAccessToken` → compatibilité héritée

### 4.2 HTML inline

Des vues historiques utilisent encore des handlers inline pour certaines interactions.

Le shell de hardening fournit désormais une couche de compatibilité contrôlée, mais cela ne remplace pas un nettoyage définitif dans chaque vue.

Les zones identifiées incluent notamment :

- `financials.js` ;
- `overview-insights.js` ;
- `alertes.js` ;
- `publications.js` ;
- `screener.js` ;
- `components.js` ;
- certains anciens templates HTML.

**Statut : 🟡 dette technique, pas panne bloquante vérifiée.**

## 5. Sécurité frontend restant à traiter

### 5.1 `localStorage`

Le token de session est toujours stocké dans `tc_session`.

Le code vérifie l'expiration du JWT côté client, mais cette vérification est uniquement une garde UX/routage. Elle ne constitue pas une preuve d'autorisation.

La vraie frontière de sécurité reste l'API et Supabase.

### 5.2 XSS

Le dépôt contient encore de nombreux `innerHTML`.

Certaines fonctions utilisent correctement une fonction d'échappement (`esc`, `finEsc`, etc.), mais une revue systématique de toutes les interpolations provenant de données externes reste nécessaire.

**Action recommandée :** cartographier chaque `innerHTML` interpolé avec une donnée réseau, utilisateur ou base, puis remplacer les constructions dangereuses par DOM APIs ou échappement systématique.

### 5.3 Content Security Policy

Aucune CSP stricte globale n'a été imposée pendant cette phase.

Raison : l'application contient encore des scripts inline et plusieurs dépendances CDN. Une CSP ajoutée sans migration préalable casserait potentiellement l'exécution.

**Action future :** migrer progressivement les scripts inline puis introduire une CSP mesurée.

## 6. Supabase : points toujours hors périmètre de modification

Aucune modification Supabase n'a été exécutée pendant cette passe.

Les sujets suivants restent à vérifier dans le projet Supabase `brvm data` :

### Paiement

Vérifier côté RPC que :

- `p_user_id` est comparé à `auth.uid()` ;
- le montant facturable est recalculé côté serveur à partir du plan et de la périodicité ;
- un utilisateur ne peut pas créer ou modifier une commande pour un autre utilisateur.

### RLS

Vérifier table par table que les opérations sensibles sur les données de marché et données financières sont protégées par des policies adéquates, notamment :

- `cours` / historique ;
- `indices` ;
- `entreprises` ;
- `financials` ;
- tables utilisateur ;
- données de paiement ;
- journal d'administration.

### Concurrency portefeuille

Le contrôle applicatif empêche plusieurs incohérences courantes, mais le verrou transactionnel définitif doit être posé côté base pour empêcher deux écritures concurrentes de passer simultanément.

## 7. Rate limiting

Le mécanisme de limitation actuel protège au niveau de l'instance d'exécution.

Il n'est pas une garantie globale entre plusieurs instances serverless.

**Action future :** store partagé (par exemple Redis/solution équivalente) si une protection globale devient nécessaire.

---

## 8. Scraping BRVM

Le scraper reste dépendant de la structure HTML de `brvm.org`.

Le contrôle de variation en aval limite le risque d'écrire une donnée manifestement aberrante, mais ne transforme pas le parsing HTML en flux contractuel.

**Action future :** source structurée/API/flux officiel lorsque disponible, avec schéma explicite et tests de contrat.

## 12. Conclusion

Le diagnostic a changé depuis l'audit historique : le principal problème n'est plus une panne structurelle immédiate du shell de production.

Le socle **build + assets + router + header/sidebar + bootstrap** est maintenant stabilisé et vérifié en production.

La dette restante se concentre principalement sur :

1. la sécurité Supabase/RLS/RPC, qui n'est pas vérifiable uniquement depuis le dépôt ;
2. la surface XSS liée aux `innerHTML` et au token `localStorage` ;
3. les reliquats d'handlers inline ;
4. la complexité CSS ;
5. la dépendance du scraper à la structure HTML ;
6. le manque de validation navigateur automatisée complète.

**Aucune de ces dettes ne justifie une réécriture complète de `app.html`, un remplacement immédiat de la stack ou une modification arbitraire des APIs et données de marché.**

La stratégie correcte reste : **stabiliser → vérifier → cartographier → corriger module par module → tester → seulement ensuite simplifier l'architecture.**
